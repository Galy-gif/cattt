## 原因与改动

`AppStore.advanceConditions` 每帧调用 `YardRuntime.facts`。虽然 Runtime 对相同事实去重，调用前仍会计算水碗是否在今天加满，并在 Runtime 内构造字符串键；这些工作跟随原生显示时钟反复执行。

现在水碗日期或邮件标志变化时立即调用事实同步，每秒条件时钟保留一次检查，处理跨日失效和恢复。没有新增事实缓存；沿用原有去重、队列和初始化配置。倒水进度、旗子和天气过渡继续走原帧循环。

## 实际运行对照

Xcode 27.2、iPhone 18 Pro / iOS 27.0 Simulator、Debug，固定调试小时 12、晴天、空碗，镜头 following。基线为第四批加同一 Debug 计数与契约探针。两个页面各采集一次约五秒窗口，计数发生在真实 `YardRuntime.facts` 方法入口。

| 场景 | 修改前检查次数 / 窗口 | 修改后检查次数 / 窗口 |
|---|---:|---:|
| 院子 | 307 / 5.183s | 5 / 5.133s |
| 聊天 | 312 / 5.224s | 5 / 5.144s |

稳定状态下检查频率由每秒约 59 次降至约 1 次；状态变化会额外触发即时检查。四个窗口的网页 surface 均 ready，Store 通知均为 0。原始时长、计数及契约结果见 [量测.json](量测.json)。本轮量测调用次数，没有采集 CPU 时间、真机耗电或 FPS，也不能把去重前的检查次数当成实际 JS 消息数。

## 验证

- 实现前增加 `factsCheck`，在同一 MainActor 调用中检查 Store 变化是否已更新待同步配置。基线的满碗、新邮件即时检查为 false；修改后满碗、清空、升旗、放下旗子四项均为 true，状态变化无需等待下一渲染帧进入同步配置。
- 模拟昨日水碗与错误的满碗网页事实，触发每秒检查后恢复为空碗；修改前后均通过。这是受控跨日条件检查，并非连续运行跨过真实午夜。
- 实际模拟器倒水和新邮件后，经内容进程终止回调注入重载，网页 ready/surfaceReady 均为 true，无失败，记录的恢复前后世界快照相等；原生业务快照保留满碗和邮件。此为回调注入，未杀死真实 WebContent 进程。
- 停止并重开 App 后，已保存的满碗状态保留；新邮件标志设为 true，再打开信箱，邮件标志变为 false，水碗仍满。日记原有两条测试记录显示正常，读取/保存错误均为 false。
- `sh tools/check_all.sh` 通过，包括跨端规则、世界层逻辑、日记/创建存储、网页 39 项测试及前后端类型检查；Debug 和 Release 模拟器构建通过。Release 的 6 个既有警告与第四批相同。
