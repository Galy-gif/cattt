# 性格、情绪与 Soul 成长 · 2026-09-12

状态：初版代码已实施：团子底色、版本化明确习惯调整、有期限状态及世界活动联动；自动成长和连续情绪曲线尚未完成。实际范围见 [实施验收](后端与Agent循环-实施验收-2026-09-12.md)。下文为完整目标方案，不代表全量交付。

依据：[猫的个体差异机制](../产品/猫的个体差异机制.md)、[产品需求](../产品/产品需求-方向草案v0.2.md)、[开发者版后端](后端-开发者版-2026-09-11.md)。成长档案模板见 [Soul.md](../产品/Soul.md)。

## 1. 体验目标

同一只慢热猫，刚认识时通常等你开口；经历真实的共同互动后，逐渐形成自己的偏好、习惯和表达方式，例如开始主动分享某类观察。成长能跨会话保留，同时仍让人认得出原来那只猫。

以上是目标示例，不代表团子已经有这些经历。用户今天说累了，首先改变本轮回应；不会因此永久把猫变得沉默。猫刚醒时精力可以逐渐恢复，但已经形成的习惯不会随着情绪恢复而消失。

## 2. 对象与责任

| 对象 | 保存什么 | 变化方式 |
|---|---|---|
| 基础性格 PersonalityProfile | 用户设定的默认倾向、允许的变化范围、基础行为规则 | 用户调整或明确版本迁移；成长不直接覆盖原始配置 |
| 成长档案 Soul | 逐渐形成的偏好、习惯、情境反应和自我表达；对基础倾向的有限长期调整 | 有来源的经历支持后形成新版本，跨会话保留 |
| 临时状态 RuntimeState | 当前精力、情绪、兴趣与活动意愿，更新时间和触发来源 | 事件改变，按时间恢复；具体维度与速度待标定 |
| 关系状态 RelationshipState | 相处许可、距离、边界、共同仪式 | 真实互动与明确许可更新；熟悉不自动授予权限 |
| 记忆 Memory | 发生了什么、用户说过什么、事实与偏好 | 沿用提取、纠正、删除和来源规则 |
| 世界状态 WorldState | 猫在哪里、正在做什么、已发生的世界事件 | 世界事件持久化后进入聊天；画面负责表现 |

“用户喜欢雨”是一条记忆；“猫经过多次真实经历逐渐喜欢观察雨”才可能是 Soul 成长。单纯为了满足用户口味而复制用户偏好，不能算猫的成长。

## 3. Soul.md 的形式

仓库中的 `docs/产品/Soul.md` 已按同日用户补充写为团子的初始档案：外表有些高冷、内心细腻，表达有“喵”等猫咪特征；初始没有成长事实。其章节结构可复用，团子的具体设定不自动套给其它猫。运行时每只猫拥有独立的 Soul 内容和版本；不能让所有猫共用一份会被覆盖的文件。

建议以 PG 中的版本记录为权威数据，保存 Markdown 正文、结构化成长条目、来源、父版本、生效时间和修订原因。`Soul.md` 是该版本可阅读、可导出的表达形式；运行时不同时维护一个可独立编辑的磁盘副本，避免两份内容分叉。表名和接口名在实施时确定。

正文适合阅读；行为编译使用通过校验的结构化条目。两者在同一次版本提交中生成。模型可以提出修改候选，不能直接覆写完整档案或写入任意系统指令。

每条成长至少包含：稳定 ID、所属猫、类别、内容、可观察的行为影响、适用情境、来源事件 ID、状态、形成时间和修订原因。状态区分候选、生效、被替代和撤回；候选不参与行为生成。

## 4. 什么可以成长

建议首版支持三类：

- **偏好与习惯**：逐渐偏爱某类真实世界活动，或形成自己的分享方式。
- **情境反应**：在有依据的特定场景中，逐渐更愿意主动、更耐心或更善于表达。
- **表达方式**：形成经过真实互动确认的共同用语和表达习惯，允许普通表达，避免固定口癖。

成长可以有限改变实际默认倾向，因此不只是追加回忆。调整相对基础性格的累计偏移也必须受约束，不能每次小改、最后完全变成另一只猫。首版保留现有四项配置；探索偏好是否增加为第五项不在本轮定案。

猫的身份、用户明确设置、事实与边界不由成长覆写。超出连续性范围的改变先留为候选，需要用户确认后作为显式性格调整。范围和证据阈值须通过固定场景比较确定，不能现在凭空指定数值。

## 5. 成长怎样发生

1. 聊天或世界产生真实、已持久化的事件。世界动画播放、模型自己编出的故事不能直接成为共同经历。
2. 当前消息先用于本轮需要判断和临时状态；回复成功落库后，异步分析是否有长期成长候选。
3. 候选必须引用有效来源，检查它是事实、短期感受、关系许可还是猫的长期变化。重复处理同一事件不能增加证据强度。
4. 用户明确提出的习惯调整可作为直接依据；系统自行归纳的成长需要多个独立经历支持，用户沉默和没有反对不算许可。
5. 规则校验来源、边界、冲突与累计偏移；通过后提交一个新版本，从后续轮次生效。证据不足则保留候选或舍弃。
6. 后续反例可修订或撤回成长。用户纠正和撤回许可立即影响可用行为，不等待异步整理结束。

用户情绪低落不等于猫也低落；猫可以理解并调整回应，同时保持自身状态。未使用 App 的时间不产生“被冷落”、惩罚或催促，也不会虚构离线共同经历。

删除来源或要求不再提时，依赖该来源的成长必须重新检查，失去依据的条目停用；不能从 Soul 的旧正文恢复已删除内容。历史版本和导出也要遵守删除与撤回规则；删除后可以保留无正文的修订元数据，但不承诺完整重放被删除的内容。

## 6. 一轮行为闭环

`基础性格 + 生效 Soul → 默认倾向 → 当前需要、临时状态、关系许可与边界约束 → 行为计划 → 文字与院子表现`

状态按服务端时间从上次更新时间推进，再应用尚未消费的新事件。情绪逐渐回到基线，兴趣可以到期；Soul 的长期变化不按这套规则衰减。

当前消息需要在生成前影响状态，但以消息/事件为去重依据：同一消息的重新回复、网络重连、重复投递不能再次改变状态。回复失败不撤销已经发生的用户输入；失败或作废的猫回复不作为成长证据。首版建议只从完整成功的猫回复提取成长，停止的半句不使用。

每轮固定所用的基础性格、Soul、状态和关系版本，记录事件来源、记忆 ID、行为计划及最终结果。生成过程中有新边界时仍按最新边界约束发布；不能以旧快照绕过撤回。

服务端拥有语义状态，iOS 拥有动画播放、路径和帧进度。先做聊天状态与追踪，再让院子按同一状态选择现有可播放动作。动作开始/完成通过有 ID 的事件回报；计划去睡不等于已经睡醒。断网时可继续表现已知状态，但不能生成已发生的服务端经历。

不需要后台每秒模拟：读取时按经过时间推进可计算状态，真实世界事件另行记录。暂不增加主动消息或推送。

## 7. 实施顺序与验收

| 步骤 | 交付 | 必须看到的结果 |
|---|---|---|
| 1 文字中的性格与成长 | 基础性格编译、独立 Soul 版本、来源及行为追踪 | 同场景不同配置有行为差异；同猫成长前后有变化且保持连续性 |
| 2 临时状态闭环 | 事件更新、时间恢复、状态快照 | 同一事件只更新一次；困倦能恢复，已生效成长仍保留 |
| 3 院子联动 | 共享语义状态、现有动作映射、真实事件回报 | 聊天知道已确认活动；没有素材的动作不假装播放完成 |

第 1 步同时需要明确第 2 步接口边界，避免把临时情绪先写进 Soul。无需等整个后端重构完，但涉及终态竞争、持久化异步待办和幂等的部分必须先解决或随功能解决，参见待评审的[后端架构优化](后端架构优化-2026-09-12.md)。

验证场景：中性闲聊、分享好消息、低落且不要建议、征求意见、结束、越界修复，以及成长前后、跨会话和 30–50 轮对话。固定模型、基础记忆和场景，仅改变待测的性格/Soul/状态变量。

工程验证覆盖：重复事件与重试不重复成长；并发候选不覆盖版本；无效来源不能生效；撤回即时约束；删除来源后派生成长失效；多次小改的累计偏移受限；时间恢复不改 Soul；失败回复不产生虚假成长；不同猫档案隔离。

自动检查验证状态与数据规则；隐藏配置的人工比较验证辨识度、自然度和身份连续性。具体数值门槛由首轮样本标定。当前没有这些验收结果。
