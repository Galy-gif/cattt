## 目标与范围

先让一轮回复的状态、落库和异步收尾有明确的责任归属，再整理 HTTP 与记忆模块。保留本机单实例、Hono、Drizzle/Postgres、Redis/BullMQ、AI SDK；保持一猫一段连续对话、现有 REST/SSE 字段、停止保留可见文字、未开口才作废、记忆轮询等行为。

本轮不扩展部署、多实例、向量召回或产品能力。生成仍在 API 进程中运行且独立于 HTTP 连接；不新增微服务、通用事件总线、通用 Repository 或依赖注入框架。

## 当前问题与证据

以下来自静态调用链检查；异常和并发场景尚未做故障注入，不能当作已复现事故。

| 优先级 | 代码位置与现状 | 影响 |
|---|---|---|
| 第一批 | `server/src/turns/run.ts`：完成事务之后 `publish(done)` 仍在生成的总 `try/catch` 内；`fail()` 无前置状态条件 | 发布抛错会尝试把已完成轮次改为失败，猫消息却已存在 |
| 第一批 | `run.ts` 的完成、停止、作废写入没有统一状态条件；`worker/sweep.ts` 独立标记失败 | 清理与晚到的生成结果可能互相覆盖终态 |
| 第一批 | `run.ts` 完成后记忆入队失败只记日志，停止后的入队错误被吞；边界接口先落库再入队 | 队列故障后没有持久化的补投流程；已有 `extractedAt` 只能表示完成，不能保证任务被执行 |
| 第一批 | `turns/events.ts` 的 `tail()` 只在进入时检查键是否存在，空读一直 ping | 流存在但终止事件没写入时，数据库已结束，监听仍可能一直等待 |
| 第二批 | `worker/memory.ts` 同时负责提取模型、筛选、冲突与数据库写入；删除在 `api/app.ts` | 删除和候选写入没有共同的串行化边界；不同来源的同一方面记忆可并发竞争 |
| 第二批 | `queue.ts` 按用户消息去重，但 job payload 和 `extractedAt/remembered` 属于 turn | 同一消息重新回复后，已有 job 可能使新 turn 无法得到自己的提取完成标记 |
| 第三批 | `api/app.ts` 包含猫更新、历史查询、记忆删除事务和边界写入；`runtime/model.ts` 同时依赖 AI SDK、PG 和 BullMQ | HTTP、业务规则和基础设施修改互相牵连，局部测试需要加载无关连接 |

此外，锁续租结果在 `run.ts` 未检查，错误被吞；首字复核与 `firstTokenAt` 写入之间仍有并发窗口。第一批必须明确失锁和首字竞争的处理，不能只拆文件。

## 推荐边界

| 边界 | 负责什么 | 关键接口（示意） |
|---|---|---|
| `api/` | 参数、身份、HTTP 状态、JSON/SSE 编码 | 路由调用用例；SSE 读取事件和终态快照 |
| `turns/service.ts` | 发送与重新回复的用例编排；返回已持久化的轮次 | `send(owner, input)`、`reply(owner, messageId)` |
| `turns/store.ts` | 创建、认领、首字资格、终态提交及事务 | `claim(turnId)`、`commitOutcome(turnId, outcome)`，返回 applied 或已有终态 |
| `turns/run.ts` | 等锁、组上下文、消费模型流、响应取消 | 接收明确的 store、模型、事件、锁依赖；不负责 HTTP |
| `turns/events.ts`、`turns/lock.ts` | Redis 流/取消和锁租约，分别集中错误与资源释放 | `publish/tail`；获取、续租、释放及失锁通知 |
| `jobs/` 与 `worker/` | PG 中待办的恢复、BullMQ 投递与执行生命周期 | 补投、领取、完成、有限重试；worker 调用业务模块 |
| `memory/` | 候选写入、删除阻断、召回和提取结果 | `applyCandidate`、`deleteMemory`、`recall`、提取用例 |
| `runtime/` | 性格、上下文格式、模型选择和供应商错误归类 | AI SDK 类型可留在模型调用边界内；BullMQ 错误转换移到 worker |

只在需要隔离副作用、故障注入或复用事务规则的位置提供具体依赖参数。简单查询不必套接口；不做逐表 CRUD 抽象。PG/Redis/Queue 连接在进程入口组装与关闭，业务模块的 import 不应顺带启动队列连接。

## 第一批：回复生命周期与可靠收尾

### 1. 统一终态提交

- `queued → generating` 通过条件更新认领；`completed/stopped/superseded/failed` 为不可互相覆盖的终态。
- 完成/停止的猫消息与 turn 更新在同一事务内；先锁定或条件认领目标 turn，再插入消息。清理任务也走相同状态约束，竞争失败的一方不再写消息和事件。
- `fail()` 只允许结束非终态；已落库后事件发布失败记为投递错误，不能重写业务结果。
- 对同一 turn 的猫回复增加数据库唯一约束作为最后保护。迁移前只读检查历史重复，若存在先报告具体数据，不自动删数据。
- 首字资格与新消息的版本递增使用共同的 conversation 事务锁协调。锁内复核轮次和版本并记录开口状态，锁外发布；保留「已开口让它说完」的已定规则。停止/作废信号在发布前再次检查。
- 续租返回明确成功/失锁结果；失锁时中止模型、禁止继续发布，并通过条件提交结束轮次。数据库心跳继续使用 `dbNow()`。

### 2. PG 保存异步待办，Redis 负责执行

新增小型待办表，仅用于记忆提取和边界整理，保存业务去重键、对象 ID、版本、状态、尝试次数、下次重试时间和简短错误；不保存对话副本。

- 完成/停止事务同时写入记忆待办；边界创建事务同时写入整理待办。
- worker 启动及周期扫描 PG，补投到 BullMQ；扫描入口不能仅依赖 Redis 中的 scheduler 存在。
- 入队成功不算业务完成。执行完成后写 PG 完成状态；已完成待办不再执行。
- 保留有界重试。不可重试及耗尽次数进入可检查的失败状态，扫描不能重新开启无限重试；已有失败的 BullMQ job 要有显式重试处理。
- 记忆去重保持「来源消息 + 类型 + 版本」。同一来源的多个成功/停止 turn 关联同一提取结果，把 `extracted/remembered` 投影给相应 turn；先明确选择的成功轮次和输入快照，禁止依赖哪个 job 恰好先入队。
- 从现有 `completed/stopped` 且未提取、未整理边界补建待办时分批并用唯一键保护。使用 mock 验证迁移；不自动批量触发真实模型调用。

### 3. 事件流终止与重放

- Redis 空读时检查 PG 终态，发现已完成但缺少终止事件时补发终止结果并结束连接；发布检查 Redis 事务每个命令的错误。
- 继续沿用现有 SSE 字段。运行中 Redis 丢失按已有可重试降级处理，不承诺恢复未持久化文字。
- 不能把 PG 全文直接追加给已经收到部分 delta 的客户端：`ios/Maomao/Store/AppStore+Remote.swift` 的 delta 是追加语义，accepted 不会清空旧文字。
- 本批保证「事件流完整保留、仅终止事件缺失」的恢复；部分流丢失/过期后的全文替换另列为客户端协同修复，实施前确定快照重置协议。不得把现有 `replayFromDb()` 直接当作所有断线情形均正确的证据。

### 验收

1. 回复事务成功后注入事件发布失败：turn 保持 completed，消息只有一条，记忆待办仍存在；流恢复后可结束。
2. 完成、停止与 stale 清理同时竞争：只一个终态获胜，失败/作废轮次不留下晚到猫消息。
3. 并发发消息、首字前补话、首字后补话：符合原有作废规则；失锁后旧执行器停止发布。
4. 入队失败、worker 重启、重复投递：待办恢复，记忆副作用幂等，重试次数有限；同来源重新回复的轮询标记最终收敛。
5. 保留现有流式、正常断线续传、停止 UTF-16 截断、重试、记忆、删除与边界 smoke；不减少既有行为覆盖。

## 后续两批

第二批统一记忆写入与删除的事务入口。在同一猫的写入事务中使用共同锁，避免空集合查询无法锁住未来插入的问题；模型请求不持锁。补并发删除/提取、同一方面不同来源写入和旧来源重放测试。处理来源顺序，避免旧偏好晚完成后覆盖新偏好；不改现有敏感度、冲突、明确要求记住的规则。

第三批按猫、聊天、记忆、边界拆路由，把事务规则移入对应模块；拆分模型选择、用量记录和队列错误适配。用 HTTP 契约测试保护鉴权、错误码、分页和返回字段，以现有 iOS 调用为准。

## 实施与回退

按第一批 → 第二批 → 第三批逐批验证；第一批内部先补回归与统一状态，再加待办迁移与补投，最后接通事件恢复。每一步保留可运行服务。

数据库迁移采用增量方式，旧字段和现有 API 保留；停 API/worker 后迁移再启动本机服务。待办 worker 与写入待办的版本需一起启用，回退时先停止新 worker，保留待办数据和新表，不通过删表回退。涉及历史重复数据另行处理。
