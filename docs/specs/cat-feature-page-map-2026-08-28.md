# 一、完整使用流程

## 首次进入

打开应用 → 简短认识产品 → 登录／注册 → 选择猫的外观 → 起始气质与可选微调 → 命名／声音 → 预览确认 → 初次见面与世界介绍 → 开始相处。

这只是推荐顺序。登录是否后移、名字在哪一步填写，可以通过原型调整。

## 再次回来

打开应用 → 回到自己的猫 → 聊天／互动／语音 → 自然接续之前的话题 → 按需查看回忆或修改设置。

## 从通知回来

点击猫的消息 → 进入对应聊天与话题 → 继续聊／延后／结束该话题。

**用户第一次需要“认识和创造”，第二次就应该直接“回来相处”，不用反复经过介绍页和选择页。**

# 三、选择猫与创建个体

这一部分要让用户理解：选的是“我的猫”，不是四个锁死的角色。

| 外观详情 | 看清毛色、花纹、体型特点；如果资源允许可转动查看 | 同页放大／详情层 | 展示方式待定 |
| 起始气质选择 | 慢热观察、活力好奇、温柔陪伴、直接爽快；说明默认相处方式 | 创建步骤 | P0，方向已确认 |
| 气质解释 | 用行为例子解释差异，而非只显示几个形容词 | 卡片展开 | P0 |
| 性格微调 | 活力节奏、主动性、表达直接度、亲近表达；可跳过 | 可选步骤／展开面板 | P0，具体文案待定 |
| 性格场景预览 | 同样的好消息、低落、征求意见场景，观察不同回应 | 创建步骤 | P0 |
| 猫的命名 | 输入名字、检查格式、可选推荐名字 | 创建步骤，可合并 | P0 |
| 声音选择与试听 | 有限声音试听、选择默认声音 | 创建步骤／后续设置 | P0／P1 待定 |
| 创建确认 | 汇总外观、名字、气质、声音；返回修改 | 确认页 | P0 |
| 创建处理中 | 保存身份与性格配置；失败重试；避免重复创建 | 页面状态 | 基础 |
| 猫的身份卡 | 名字、外观、相遇日期、自然语言性格简介 | 完成页，后续归入猫档案 | P0 |

需要明确的规则：

- 选一个起始气质，已经得到完整性格，不调也能开始。
- 四个气质不等于四种外观，外观数量仍未定。
- 同一种外观可以搭配不同气质。
- 不限定一种体型，模型数量、骨架和毛发方案以后讨论。
- Anchor、Range、Triggers 等六字段是内部机制，用户主要看行为解释和预览，不需要填写这些术语。

# 四、初次见面与世界观介绍

这一块值得设计，但未必需要“世界观介绍独立页”。

| 页面／界面 | 需要包含的功能 | 建议形态 | 安排 |
|---|---|---|---|
| 初次见面 | 猫出现、介绍自己、回应用户刚选的名字与气质 | 一次性场景／聊天开场 | P0 建议 |
| 世界介绍 | 说明猫生活在哪里，用户与这个空间是什么关系 | 初见中的短场景 | 内容与表现待定 |
| 基本互动教学 | 怎样说话、看历史、摸猫、进入语音 | 首次使用时提示 | 随功能上线 |
| 记忆说明 | 猫会选择性记住什么，哪里能查看和删除 | 简短提示＋详细入口 | P0 |
| 相处边界说明 | 可以不回复、可以离开、可以关闭主动消息 | 融入开场与设置 | P0 |
| 引导跳过与回看 | 跳过不损失功能；以后能重新看 | 按钮＋帮助入口 | 基础 |

世界观介绍至少要回答：

1. 这只猫是谁，它与用户是什么关系？
2. 它平时在哪里生活？
3. 用户能怎样参与它的生活？
4. 用户不在的时候会发生什么？
5. 哪些是虚拟世界表现，哪些是真实系统能力？

建议通过初次见面让用户理解世界，详细设定按需回看。暂时不用先写完整猫猫星球、种族历史、NPC 和长篇序章。

# 八、长期记忆与边界管理

这是核心能力，不能只留一个“开启记忆”的开关。

| 页面／界面 | 需要包含的功能 | 建议形态 | 安排 |
|---|---|---|---|
| 记忆管理首页 | 查看猫记住的信息，按偏好、目标、重要事件等组织 | 二级页面 | P0 |
| 记忆详情 | 内容、来源、时间、有效状态 | 详情页／面板 | P0 |
| 记忆更正 | 修正事实、对象、时间、过时偏好 | 编辑面板 | P0 |
| 记忆删除 | 删除选定记忆，并阻止继续使用旧内容 | 操作＋确认层 | P0 |
| 明确要求记住 | 在聊天里说“记住这件事”，显示保存结果 | 聊天反馈 | P0 |
| 记忆冲突确认 | 新旧说法矛盾时澄清，不静默覆盖 | 对话卡片／面板 | P0 |
| 敏感信息确认 | 如允许保存敏感信息，明确内容与用途并请求确认 | 确认卡片 | 规则待定 |
| “不要再提”管理 | 查看和修改已设边界；主动撤销时说明后果 | 二级页面 | P0／P1 |
| 记忆功能设置 | 是否形成新记忆、是否使用已有记忆 | 设置分组 | P0，开关拆法待定 |
| 不留长期记忆的聊天 | 明确本次是否写入记忆、日记、灵感等 | 模式／入口 | 候选 |

四类操作必须分清：

| 用户操作 | 应表达的含义 |
|---|---|
| 删除聊天记录 | 处理原始对话；是否连带删除派生内容，需要明确选择和说明 |
| 删除记忆 | 这条信息不再作为长期记忆使用 |
| 不要再提 | 为之后的互动建立持续边界，阻止相似回题 |
| 关闭记忆 | 需要说明是停止新增、停止使用已有记忆，还是两者都停止 |

不能用一个含糊的“清空”按钮覆盖这些不同需求。

需要坚持两个边界：

- 高主动性格，不等于拥有通知权限。
- 到时间，不等于一定发送。用户已取消、进入静默时段、事情已完成，都可能使消息延后或不发送。

首版主动联系只考虑消息，不做猫主动打电话。

| 共同经历时间线 | 相遇、重要交流、共同活动 | 日记内视图／独立页 | 候选 |
| 共同物件详情 | 物件是什么、为什么出现、关联哪次经历 | 场景详情层 | 候选 |
| 周期回顾 | 回顾一周／一月的重要线索，不给用户贴诊断标签 | 回顾卡片／页面 | 候选 |
| 分享回忆 | 选内容、隐藏敏感信息、预览后分享 | 分享流程 | 候选 |

关系成长不需要单独做一个“亲密度升级页”。熟悉、信任、边界和共同仪式可以通过称呼、表达、日记、动作和物件体现。

关系日记不能自动成为权威记忆：它是整理后的阅读内容，可能需要用户修改。

# 十四、容易漏掉的页面状态

这些未必增加独立页面数量，但设计和研发都需要覆盖。

| 状态类别 | 至少要设计的情况 |
|---|---|
| 登录 | 验证码错误／过期、授权取消、登录失效、账号恢复失败 |
| 创建 | 未完成、保存失败、重复点击、退出后恢复、资源加载失败 |
| 聊天 | 空记录、发送失败、生成超时、流式中断、用户打断、追加消息 |
| 网络 | 断网、弱网、重连、内容尚未同步；没有联网回复能力时明确说明 |
| 语音 | 未授权、无声、识别失败、耳机断开、来电打断、后台中断 |
| 记忆 | 没有记忆、等待确认、事实冲突、修改失败、删除处理中 |
| 话题 | 无候选、已完成、已过期、已取消、通知权限关闭 |
| 日记／灵感 | 没有内容、生成中、待确认、生成失败、原始来源已删除 |
| 世界资源 | 模型／动画下载中、资源失败、低性能设备降级、减少动画 |
| 数据操作 | 导出排队、文件过期、删除处理中、重新验证、失败重试 |
| 跨设备 | 未同步、不同设备同时修改、旧配置不能覆盖新配置 |
| 服务 | 暂时不可用、维护、版本不兼容、必要更新 |
| 跳转 | 通知指向的内容已删、链接失效、登录后返回原目标 |

不能把“网络失败”写成“猫不想理你”，也不能把服务器重试包装成猫的情绪。

# 十五、没有用户页面，但必须有的系统能力

功能清单还要包含这些，否则界面做完也不等于产品成立。

| 系统能力 | 用户最终感受到什么 |
|---|---|
| 性格编译与六字段机制 | 同样的情境，不同猫会作出不同选择 |
| 当前状态与关系适应 | 猫会变化，但不会无缘无故换性格 |
| 记忆筛选、检索与纠错 | 记得对、用得合适，改错后不再反复错 |
| 话题去重与调度 | 不重复追问，不把已经结束的事重新翻出来 |
| 权限与安全检查 | 关闭功能、拒绝建议、要求停止能够真正生效 |
| 回复可靠性 | 追加消息能被考虑，不重复回复，不漏掉用户消息 |
| 异步整理 | 记忆、话题、日记整理不拖慢聊天开始 |
| 世界事件记录 | 对话、动作、物件和共同经历保持一致 |
| 运行记录与评测 | 能定位错误、检查性格漂移、追踪质量与成本 |

内部可能需要配置、评测、问题回放、任务状态和成本看板，但它们属于内部工具，不是用户 App 的页面。

# 十六、页面架构与下一步决策

## 建议的信息架构

先围绕三个区域组织，不急着确定一定是三个底部 Tab：

| 区域 | 承接内容 |
|---|---|
| 陪伴 | 猫的主页、聊天、语音、身体互动、少量续聊入口 |
| 回忆 | 日记、灵感、共同经历；提供话题与记忆管理入口 |
| 我的 | 猫档案、性格调整、用户资料、通知、隐私、账号与帮助 |

P0 还没有足够日记和灵感时，不用放一个空的“回忆”Tab。记忆和话题先通过二级入口访问即可。

## 优先绘制的主链

1. 欢迎与登录。
2. 猫外观选择。
3. 起始气质选择与可选微调。
4. 场景预览与创建确认。
5. 初次见面。
6. 陪伴／文字聊天主页。
7. 猫档案与后续性格调整。
8. 记忆管理与纠错。
9. 话题入口与管理。
10. 设置、隐私与数据控制。
11. 对应的加载、失败、取消和恢复状态。

这不是最终“11 个页面”：其中创建可以拆成多步，确认可以用弹层，聊天可以与主页合并。

## 需要继续确认的事项

- 登录在体验前还是体验后，是否提供游客模式。
- 猫的家与聊天是同页切换，还是两个页面。
- 世界介绍用几段对话、短场景，还是独立介绍页。
- 首批身体互动究竟做哪几种。
- 性格预览的形式，以及后改性格如何提示。
- 记忆管理入口、敏感信息确认和关闭记忆的具体含义。
- 日记是否先保存草稿，用户怎样确认。
- 是否允许换猫／重建，以及如何处理原来的关系。
- 商业化何时进入，而不是提前为商店铺完整页面。

**整体上，产品可以功能丰富，但日常入口应该简单：回来见到猫，随时说话或互动；需要回看和管理时，再进入记录与设置。**
