# iOS · 3D 世界层与界面同步 · 方案 · 2026-09-17

状态：**待评审，代码未动。** 决定见 [决策-2026-09-17-iOS同步](../决策/2026-09-17-iOS同步.md)。

## 0. 这份方案解决什么

用户 2026-09-17：「web 端视觉基本上确定了，想同步到 ios 端」，并选定同步范围是**世界层 + 界面都换**；技术路线要我先出对比再定。

这推翻 [决策-2026-09-17-网页版](../决策/2026-09-17-网页版.md) 第 2 条「iOS 现状不动」，连带让 09-09「毛毡长卷 + 逐帧猫」、09-11「猫全部逐帧」在 iOS 上退役（不是立刻删，见第 6 节）。那一条原话里留的前提是「等网页版站稳、实测 WKWebView 后再定」——实测这一步没有跳过，它就是本方案的第 0 轮。

本方案回答四件事：走哪条技术路线（第 1–2 节）、iOS 这边谁管什么（第 3 节）、两端差多少（第 4 节）、分几轮做和每轮怎么算过（第 5–7 节）。

## 1. 两条路线的对比

**路线 A · WKWebView 内嵌**：App 里放一个 WKWebView，加载打进包里的 `web/` 院子（只要院子画布，不要滚动页面）。Swift 和网页之间走消息桥。

**路线 B · 原生重写**：用 SceneKit 或 Metal 把院子和团子重做一遍，glb 转成原生格式。

下面的数都来自仓库里量过或数得出的东西，出处在括号里。

| | A · WKWebView | B · 原生重写 |
|---|---|---|
| **要新写的代码** | 院子专用入口、竖屏跟随镜头、触摸与点选、消息桥：TS 约 500–600 行；Swift 宿主约 300 行 | 把现有运行时整个搬一遍：`world.ts` 850 + `felt.ts` 113 + `atmosphere.ts` 201 + `renderer.ts` 148 + 团子运行时（`tuanzi.ts`、`procedural.ts` 297、`model.ts`）约 900 + `cat.ts` 247，合计 **约 2,400 行 TS/GLSL**，其中自定义着色器 9 个（毛毡、草、水、天空、星、雨、团子绒毛壳、辉光、收尾调色） |
| **和网页版是不是同一个样子** | 同一份代码、同一份 glb，天然一致 | 着色器逐个重写，毛毡颗粒、草的风、水的针脚纹、绒毛壳每一个都要重新对一遍色；ACES 调色和辉光也要重做 |
| **团子还在改** | Codex 每改一版模型／动作，导出一次 glb，两端同时更新 | 每一版都要再转一次格式、再验一遍；程序层（看向、眨眼、尾巴弹簧、锁脚 IK）两份实现要保持同步 |
| **像素负担** | 手机比电脑轻得多：电脑 1440×900 按现行上限 1.5 倍是 2.9 Mpx；iPhone 17 Pro 402×874 按现行小屏上限 1.25 倍是 **0.55 Mpx，约五分之一**。场景本身约 200 次绘制、23 万面（第一轮实测），加绒毛壳约 7.2 万面 | 同样的场景，少一层浏览器开销，上限更高 |
| **帧率** | **未知，必须真机量。** 电脑上三轮都没有可信读数（预览窗口不在前台、模拟器占着 GPU）；模拟器里的 WebGL 走 SimMetalHost，也不能当真机数 | 未知，但余量更大 |
| **发热与耗电** | 风险项。陪伴类 App 会长时间开着，60fps 的后期 + 阴影 + 1.58 万根草不一定撑得住十分钟不烫 | 风险较小，但同样要量 |
| **启动** | 电脑本地 0.8–1.5 秒到可交互；手机上要再量。需要一张静态院子图盖住加载 | 更快，资源直接进显存 |
| **包体** | 两个 glb 2.26 MB + 脚本约 1 MB + 标题字体子集约 0.3 MB（`.woff` 和用不到的子集不进包）。现在 2D 世界层素材是 **约 84 MB**（场景 54 + 猫帧 30） | glb 转出的模型几 MB，同样远小于 84 MB |
| **触摸、点选** | 现在**一行触摸代码都没有**（网页版只认鼠标）。拖镜头、点猫、点信箱要在网页里新写（射线点选），再把结果发给 Swift | 原生手势，和 SwiftUI 同一套 |
| **无障碍** | 画布对旁白是一块黑盒；地点轨、状态句这些本来就是 SwiftUI 盖在上面，能读 | 同左，世界层本身两条路都读不了 |
| **系统限制** | WKWebView 从 iOS 15 起有 WebGL2，最低 iOS 17 没问题。本地文件要走自定义 scheme 才能加载 ES 模块和 glb；切后台会丢 WebGL 上下文，要写恢复 | 最低 iOS 17 卡得紧：RealityKit 的大规模实例化（草）要 iOS 18 以后的接口，**待核实**；SceneKit 已进入只维护状态。实际多半是 SceneKit + 着色器修饰，或者直接写 Metal |
| **走错了怎么办** | 第 0 轮只是一个调试入口 + 一个新的网页入口文件，不碰现有世界层，量完不行就删，损失很小 | 要写完大半才知道像不像，回头成本高 |

**两条路线都省不掉的活**（所以不算进对比）：
- iOS 的模拟逻辑要从「逐帧」解绑（第 3 节）。
- 团子的动作缺口：iOS 57 种，3D 只有 7 段（第 4 节）。这是整件事里最大的一块，是 Blender 的活，和渲染路线无关。

## 2. 建议

**建议走 A，并且用第 0 轮的真机实测当闸门。**

理由只有一条是决定性的：团子的模型还在一版一版地改，院子的材质也刚定。这个阶段两端共用一份代码，才谈得上「同步」；现在就分叉成两套渲染，之后每一次视觉改动都要做两遍、对两遍色。A 的全部风险集中在帧率、发热、启动这三个能量出来的数上，而且量的成本很低。

闸门不过的退路按顺序：关辉光 → 阴影图 2048 降 1024 → 草的数量减半 → 绒毛壳 4 层降 2 层 → 锁 30fps。每退一步都出对照图给你看值不值。全退完还不过，再回头谈 B，那时候网页版也更稳了，重写的靶子不会再动。

## 3. iOS 这边谁管什么

现在 iOS 的世界层不是「模拟算状态、渲染只管画」这么干净。调查结论（出处见本节末）：

- **模拟深度绑在逐帧上**：速度单位是精灵身长（100.9pt）；转身只能在落脚帧上换向（假定 6 帧一个循环）；树窝、喝水、情绪每一段的时长等于对应帧时长之和，测试也按这个断言；朝向只有左／右一个布尔值。
- **渲染里藏着逻辑**：按猫的 y 手排遮挡层、`-front` 前景切片、窝的轮廓遮罩、腾空时的重心偏移、水面波纹、点击区域，都在 `WorldView.swift` 里。换成 3D 以后这些由真实的深度和射线点选代替，整块不用搬。

所以分工重新划：

| | 归谁 | 说明 |
|---|---|---|
| **想去哪、什么时候去、为什么** | Swift（留下） | 性格作息、情绪、夜里雨天哪里不去、喝水时机、聊天里让它走、开门迎接。这是「脑子」，`Personality`、`WorldMood`、`AppStore+Conditions`、`WorldBridge` 基本不动 |
| **怎么走过去、怎么转身、播哪段动作** | 网页（新） | 网页版已经有：同一张路网上的寻路、连续转向、按实际速度配步频、锁脚防滑步。iOS 不再自己积分位置 |
| **镜头** | 网页（新写竖屏跟随镜头） | 镜头每帧都要动，放在 Swift 再传过去会晚一帧。Swift 只发「看某处」「找团子」 |
| **拖动、点选** | 网页收触摸、做射线点选，把「点了谁、屏幕上哪一点」发给 Swift | 信箱抽纸的起点位置就用这个点 |
| **时段天气** | Swift 定，发给网页 | 真实天气、手动三选一（09-16 决定）都在 Swift；网页的预设表本来就是照 `Atmosphere.swift` 抄的同一张时刻表 |
| **盖在院子上的一切界面** | SwiftUI（留下） | 地点轨、状态句、找团子、聊会儿、头像、信箱纸、我的 |

**消息桥**（JSON，草案，评审后定稿）：

- Swift → 网页：`atmosphere{hour|slot, weather}`、`goTo{place, gait}`、`teleport{place}`、`look{place}`、`findCat`、`act{name}`（坐、起、喝水……）、`bowl{full, pouring}`、`flag{up}`、`pause{on}`、`reduceMotion{on}`。
- 网页 → Swift：`ready`、`cat{nearestPlace, moving, offscreen}`（有变化才发，外加低频心跳）、`arrived{place, interrupted}`、`tap{target, x, y}`、`perf{fps, scale}`、`contextLost`。

**对现有代码的影响**：
- `WorldSimulation` 拆成「意图层」（留）和「位移层」（退役）。`WorldView.swift`、`WorldCamera`、`WorldDepth`、`WorldTextureCache`、`CatAction` 目录在 3D 验收通过后退役。
- 测试：`PersonalityTests`、`WorldMoodTests`、`WorldBridgeTests` 不受影响；`WorldSimulationTests` 里的路线和作息部分改成对意图层断言；`WorldV4/V5/V6Tests`、`WorldInteractionTests`、`WorldCameraTests`、`WorldDepthTests` 断言的是逐帧时长和 2D 镜头，随 2D 一起退役。网页这边的位移由现有的滑步／切换量测（`metrics.ts`）把关。
- 调试脚本：`place`、`moveCat`、`findCat`、`time`、`weather`、`mood`、`bowl`、`drink`、`diary`、`snapshot` 保留并转发到网页；`action`、`frame`、`depth` 是逐帧专用，退役。

出处：`ios/Maomao/Model/WorldScene.swift:218-232,420-504`、`WorldInteraction.swift:50-82`、`Features/Home/WorldView.swift:286-479`、`web/src/yard/cat.ts:6-19,131-247`、`web/src/tuanzi/tuanzi.ts:166-233`。

## 4. 两端现在差多少

### 4.1 院子

路网是同一张：`assets/yard-3d/make_paths.py` 直接从 iOS 的 `scene.json` 换算出 26 个节点、25 条边、六处落点和池塘轮廓。六处地点一一对应。

| iOS 有的 | 3D 院子 |
|---|---|
| 树、蘑菇屋、木牌、草丛、猫窝、栅栏、吊窝与吊绳、花、池塘、亮灯的窗 | 都有 |
| 信箱（旗子会动）、水盆 | 都有，旗子已经能动 |
| **栅栏上的横杆（团子爬上去趴着的那根）** | **没有**，要补建 |
| `grass-front`、`bed-front`、`nest-front` 这些前景切片 | 不需要，3D 里是真遮挡 |
| 水壶倒水、水滴 | 没有，要补（可以先做成简化版） |

### 4.2 团子的动作（最大的缺口）

3D 现有 7 段：待机、走、原地踏步转身、坐下、坐着、起身、抖耳；程序层有看向、眨眼、尾巴弹簧、锁脚。

iOS 现有 57 种动作里，约 40 种没有对应。按「用户每天看得见的程度」排优先级，建议这样分批补（每批都是 Blender 的活，接口约定见 5.3）：

| 批 | 动作 | 为什么排这 |
|---|---|---|
| 一 | 趴睡呼吸（猫窝）、打瞌睡点头（门口）、喝水三段（低头、舔、抬头） | 睡和喝是一天里占时间最长的两件事；喝水还连着「每天倒水」这个交互 |
| 二 | 门口情绪待机：歪头、理毛、开心、闷着、难过（进／持续／出） | 09-12 定的三种情绪靠这些表达 |
| 三 | 树窝进出（起跳、抓、爬进、窝里看、窝里睡、爬出、落地）与吊窝摆动 | 最有辨识度，但段数最多、接触点最难；网页版现在也明说猫不进吊窝 |
| 四 | 池塘玩水（看、伸爪、拍、甩）、栅栏横杆（够、爬、趴）、扑花、抓树、追尾巴、伸懒腰、跑 | 偶发的小戏 |

09-16 为 2D 逐帧写的《团子自然动作规范》里关于喝水、坐下起身、转身的**节奏要求**对 3D 同样有用，做动作时拿来当判据；其中出图、帧数、口碗对位那些 2D 专属的部分不再适用。

第一批没到位之前，对应行为先降级：睡觉用「坐着」顶，喝水先走到盆边低头待机。降级期间状态句照常，不写「敬请期待」之类的话。

### 4.3 界面

网页版的界面语言当初就是照 iOS 定的（米白薄面、珊瑚唯一强调、宋体标题、入夜换浅字、圆角三档），所以这一层**要回灌的不多**，只有网页版后来新定的细节：

| 网页版定了什么 | iOS 怎么落 |
|---|---|
| 字号按角色分档，中文加 1，最小 12 | 对 `Typography.swift` 过一遍，把小于 12 的找出来归档；不新开档 |
| 控件族动效三档 80／160／240ms，退场快一档、不回弹；场景族保持慢 | `Metrics.swift` 的动效时长归成这三档；SwiftUI 有真弹簧，slow 档的 0.12 回弹直接用 |
| 按下反馈：内缩 1px，不用缩放 | `Components.swift` 里按钮的按下态照此改 |
| 状态句「团子 · 池塘 · 黄昏 · 晴」 | iOS 聊天页页首已经是这个句式，首页状态句对齐 |
| 悬停高亮、焦点环、光标微粒 | 触屏没有悬停，不搬 |

动这些之前按 `maomao-ui` 技能的检查表过一遍；[页面底与中性族](页面底与中性族-方案-2026-09-16.md) 那份还在待评审，本方案不替它做决定。

### 4.4 跟着世界层一起要换的图

团子换成 3D 以后，下面这些还是 2D 毛毡画风，会和院子对不上：

| 素材 | 用在哪 | 怎么换 |
|---|---|---|
| `chat-backdrop`（预烘的虚化院子长卷） | 聊天页底 | 从 3D 院子渲一张同样比例的长卷重新烘；做法不变，仍是静态图，不在聊天页再开一个 WebView |
| 聊天页的太阳、月亮、星星、雨云、亮窗贴图 | 聊天页底的时段层 | 跟着新底图重出或改成程序画 |
| `tuanzi-canonical`、`tuanzi-aloof` | 头像、我的、聊天、回复超时 | 用 3D 团子渲静帧。头像缩到 34pt 本来就偏「橘色团块」（`ios/README.md` 资产缺口），趁这次出头部特写 |
| `scene-04`、选外观页的团子 | 创建流程 | 从 3D 院子渲静帧 |

这些不出图、不走出图委托，是从自己的 3D 场景里渲出来的，验收按「和院子同屏放一起看不看得出两种画法」。

## 5. 分轮交付

每轮先交东西给你看，过了再开下一轮。分支从 `web-desktop` 开 `ios-3d-world`（需要 `web/`）。

### 第 0 轮 · 实测（闸门）

只做量数要用的最小东西，**不碰现有世界层**：

- `web/` 加一个院子专用入口（只有画布，固定竖屏机位，能用启动参数切时段天气和让猫走一圈），和首页共用全部院子／团子／渲染模块。
- App 里加一个只在调试面板能进的页面，放 WKWebView 加载它；顺带验证自定义 scheme 加载、切后台再回来的上下文恢复。
- 在**真机**上量第 6 节的数，写进实施与验收。
- 交付：数值表 + 三档渲染倍率（1.25／1.5／2.0）的真机截图对照。现行 1.25 倍在 3 倍屏上只有约四成线性分辨率，毛毡本来就软，但要你看过才算。

### 第 1 轮 · 结构

- 竖屏跟随镜头（六处机位 + 跟猫 + 拖动 + 找团子）。**这一步先出六处机位的静帧给你定构图**——网页版的八个机位是给横屏电脑设计的，竖屏 31% 的可视宽度下要重新取景，这是结构层，先定。
- 触摸、射线点选、消息桥。
- `WorldSimulation` 拆意图层；地点轨、状态句、找团子、信箱旗子与抽纸、点水盆、聊天里让它走、时段天气、雨声，全部接到 3D 上。
- 启动盖图（按当前时段选一张静帧，3D 第一帧出来后淡出）。
- 2D 世界层**保留**，启动参数 `-world 2d|3d` 切换；3D 逐项对齐之前默认仍是 2D。

### 第 2 轮 · 动作

按 4.2 的四批补动作，每批一交；同时补栅栏横杆、水壶倒水。和 Codex 那边的分工见 5.3。

### 第 3 轮 · 界面与配套图

4.3 的界面细节回灌、4.4 的配套图重渲。全部通过后默认切到 3D。

### 5.3 和团子建模那边的并行规矩

团子的模型和动作现在由 Codex 在改（09-17 决策第 14 条），工作区里还有没提交的一版待你评审。本方案这边：

- 不改 `assets/tuanzi-3d/`、`web/src/tuanzi/`，只通过 `YardCat` 接口用它。
- 新动作的约定只有一条：**glb 里的动作名**。第 2 轮开始前把每批的动作名、起止姿势（从哪个姿势接进来、结束在哪个姿势）、接触点（嘴到水面、爪到窝沿）写成一张表放进本方案，Blender 那边照表做。
- 第 0、1 轮不依赖团子那边的任何新东西，可以立刻并行。

## 6. 不在本方案里

- **删除 2D 素材和代码**：约 84 MB 的场景图和猫帧、`WorldView` 一族。等 3D 默认开启并稳定以后**单独向你确认**再删；git 历史里永远有。
- 网页版接聊天、网页版适配手机浏览器。
- 换 WeatherKit、真机 iOS 17 验收、深色模式，这些原有遗留不变。
- 调查时顺带看到两处陈旧代码，记在这里，不在本方案里动：`Location.all` 里的落点／机位是 `scene.json` 的过期副本（只有名字和文案还在用）；`tuanzi-content` 图在工程里没有任何引用。

## 7. 判据

### 第 0 轮（闸门，真机，室温，亮度一半，不插电）

| 项 | 怎么量 | 过线 |
|---|---|---|
| 帧率 | 页面内用 rAF 时间戳记 5 分钟；白天晴、夜晚雨各一次；猫持续在走 | 中位 ≥ 55fps，最差 1% ≥ 40fps，自适应分辨率不贴 0.75 下限 |
| 发热 | `ProcessInfo.thermalState`，前台连续 10 分钟 | 不超过 `.fair` |
| 内存 | Xcode 内存表，App 进程 + 网页内容进程 | 合计 ≤ 450 MB；前后台来回切 10 次不被系统杀 |
