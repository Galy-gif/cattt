# 产品介绍、定义与定位

## 一句话定义

**猫猫（暂名）是一款移动端 AI 陪伴与自我理解产品。**用户认领一只可选择品种、命名并共同塑造性格的猫，通过文字和实时语音长期相处；猫在用户授权范围内记住重要信息，把交流沉淀为关系日记、灵感与可继续的话题，并通过身体动作和轻量猫猫世界持续呈现“它在这里生活，也在和我形成关系”。

## 产品是什么，不是什么

| 判断 | 产品边界 |
|---|---|
| 是 | 一只可共同塑造、能延续关系的 AI 猫；同时承担高频陪伴、个人记忆整理和自我理解三类价值。 |
| 是 | 有身体、有生活空间的关系型 AI。聊天、动作、世界状态和关系沉淀应互相解释，而不是四套独立功能。 |
| 不是 | 四个预先写好的人类角色换成猫皮；不保留林衡、夏栩、周禾、许野作为用户可选人物。 |
| 不是 | MBTI 或心理诊断工具；用户选择的是可感知的行为特征，不是心理学标签。 |
| 不是 | 重剧情养成游戏、通用效率助手、恋爱模拟器或专业心理支持的替代品。 |

## 产品定位

**定位关键词：**“有身体的第二自我” + “长期关系型 AI” + “低压力的猫猫陪伴”。

产品不只回答用户当下的问题，还要把零散表达转成可回看的个人线索：它知道用户在意什么、最近反复提到什么、哪些想法值得留下，并能在之后自然地接续。猫的身体和世界提供非人类的安全距离，也让关系通过动作、空间和共同物件被感知，而不只存在于聊天气泡里。

## 设计理念

1. **猫不是入口装饰，而是产品主体。** 品种、声音、动作、日常节奏和表达方式共同构成身份。
2. **人格由用户共同塑造，不由产品分配。** 从“四个固定人物”转为“一个稳定人格内核 + 可配置性格特征 + 运行时状态 + 关系变化”。
3. **稳定人格与临时情绪分开。** 猫今天困、兴奋或想独处，不应等同于人格突然变化。
4. **记忆必须可追溯、有边界、可纠错。** 系统内部保留来源和变更记录；用户可按需查看、更正、删除或禁止再次使用，但对话中不强制解释“为什么又提起”，避免破坏自然感。
5. **关系成长默认不做数值化表演。** 不展示单一亲密度条；通过称呼、主动性、共同记忆、日记、动作和空间变化让用户感到关系在发展。
6. **弱剧情，强日常互动。** 猫可以自己睡觉、玩耍、探索和带回小物，但不依赖连续主线、邻居 NPC 或庞大世界观才能成立。
7. **不以负罪感换留存。** 用户离开不会导致猫挨饿、生病或责备用户；主动消息可关闭、可调频，且不制造虚假危机。
8. **非恋爱边界与安全能力是底层要求。** 不诱导占有、排他或情感绑架；危机情境给出现实支持路径。

## 目标群体

**已确认的首要目标人群：**18–25 岁女性。该选择是首发策略，不等同于已经完成市场验证。

| 维度 | 当前假设 | 仍需验证 |
|---|---|---|
| 生活状态 | 社交并不一定匮乏，但现实关系难以承载高频、小颗粒、非评判的交流。 | 哪些时刻最想找 AI 猫：睡前、通勤、独处、情绪波动还是灵感出现时。 |
| 产品倾向 | 对猫、虚拟宠物、角色陪伴、AI 对话或个人记录中的至少一类有兴趣。 | “猫的身体”“长期记忆”“自我理解”三种价值的真实优先级。 |
| 核心期待 | 希望被持续理解，但不想每次重新解释自己；也不希望被诊断、说教或要求回应。 | 用户愿意把哪些信息交给系统记忆，以及需要什么可见性和控制感。 |

## 核心任务

| 用户要完成的任务 | 产品应提供的结果 | 第一层成功信号 |
|---|---|---|
| 随时说一点小事 | 低门槛开始文字或语音交流，不要求先选任务或整理问题。 | 用户能自然开口，不需要学习提示词。 |
| 被连续地理解 | 猫能在合适时机自然接续过去，并避免错误、越界或机械复述。 | 用户能分辨“记得我”和“套模板”。 |
| 创造“我的猫” | 品种、名字、声音和性格组合形成稳定且可感知的个体。 | 用户能描述它与其他猫的不同。 |
| 更理解自己 | 对话可沉淀为关系日记、灵感卡和反复出现的话题线索。 | 沉淀物能帮助回想、继续或做一个小行动。 |
| 感到它“在生活” | 猫在轻量空间中有动作和节奏，用户的互动会留下可见痕迹。 | 离开聊天页后，角色仍保持存在感。 |
| 安全地保持距离 | 用户可控制记忆、主动消息、声音和关系强度；不被催促或绑架。 | 关闭或拒绝功能不会被猫惩罚。 |

## 首阶段目标与非目标

**首阶段目标：**先证明用户能创造一只行为稳定、可辨认、会正确延续关系的猫，并愿意在多个会话中持续回来。具体留存、使用频率和满意度目标值均为 **[待产品与数据确认]**，本稿不虚构阈值。

**首阶段非目标：**不以完整虚拟世界、多人社交、复杂商业化或内容推荐证明产品价值；这些能力不能成为核心陪伴体验成立的前置条件。

## P0 可验收行为

1. 用户完成创建后，在一组固定测试场景中能观察到所选性格特征的差异；差异不能只靠口头自称或固定口头禅。
2. 同一只猫跨多轮、跨会话保持身份与核心行为一致；临时情绪变化有原因，并且不会永久覆盖人格。
3. 猫引用过去信息时，系统内部能追溯到来源；用户按需查看并删除或更正后，旧内容不再进入后续召回。对话中不要求猫每次解释提起原因。
4. 用户拒绝建议、关闭主动消息或降低亲近表达后，猫接受边界，不抱怨、不惩罚、不制造愧疚。
5. 当信息不足或记忆冲突时，猫澄清而不是编造；用户明确纠错后及时更新，旧偏好不得继续压过新偏好；安全规则优先于人格表现。
6. 文字回复开始不被记忆抽取、话题生成或日志整理阻塞；这些任务在回复后异步完成。具体首字延迟和流式体验指标待技术验证后写入验收门槛。

# 人物和世界设计

## 从“四个人物”转为“用户创造的一只猫”

**已确认：**新产品不保留四个固定人物。原来四种人物性格可以被拆成行为样本和特征区间，帮助我们理解“安静/活跃、主动/等待、委婉/直接”等差异，但不能换名字后变成四只预设猫。

**重要边界：**猫品种与性格分开。品种主要影响体型、毛色、动作范围和可能的声音适配，不默认给真实猫品种贴上“高冷、黏人、聪明”等人格标签。

## 角色模型建议

| 层 | 包含什么 | 谁能改变 |
|---|---|---|
| 猫的身份 | 品种、名字、外观、声音、初始偏好。 | 用户明确设置；部分信息可后改。 |
| 稳定人格内核 | 用户选择的行为特征，以及尊重边界、不操控、不伪装现实能力等不可关闭的底线。 | 用户可在受控范围调整；底线不可关闭。 |
| 运行时状态 | 精力、情绪、当前兴趣、是否想玩、是否想安静等短期状态。 | 由时间和事件变化，用户可影响但不能直接“改人格”。 |
| 关系状态 | 熟悉、信任、边界、共同仪式和已确认的共享记忆。 | 由长期互动与明确授权累积。 |
| 表达实现 | 措辞、语速、停顿、动作、主动消息和世界反馈。 | 系统根据以上四层生成。 |

## 用户可见的性格特征：候选，不是定稿

首版不建议直接展示“支配性、亲和性、依恋类型”等抽象心理学词。用户应调节可观察的行为差异，并能在预览里马上看见结果。

| 候选特征 | 低 ↔ 高 | 主要影响 |
|---|---|---|
| 活力节奏 | 安静从容 ↔ 活跃跳脱 | 回复长度、语速、动作频率与话题切换速度。 |
| 主动性 | 等你开口 ↔ 主动发起 | 是否追问、是否发起新话题、主动消息的表达方式。 |
| 表达直接度 | 委婉铺垫 ↔ 直接坦率 | 建议、不同意见和边界提醒的表达方式。 |
| 探索偏好 | 喜欢熟悉 ↔ 好奇探索 | 新话题、世界活动和提出新尝试的概率。 |
| 亲近表达 | 克制陪伴 ↔ 明显黏人 | 称呼、情感表达、身体动作和共同仪式；无论高低都不能越过用户边界。 |

## 性格自定义方案与实现难度

| 方案 | 用户体验 | 优势 | 主要风险 | 难度 |
|---|---|---|---|---|
| A｜连续坐标自由拉 | 每个特征用 0–100 连续滑杆，任意取值。 | 自由度和“是我创造的”最强。 | 用户期待每一点都有精确差异，但生成模型很难稳定兑现；组合与评测规模爆炸。 | 5/5 |
| B｜离散特征自由组合 | 每个特征选择低/中/高，允许任意组合。 | 仍有较强所有权，规则与 UI 比连续坐标清晰。 | 5 个特征已有 3⁵ = 243 种组合；冲突组合需要优先级和一致性测试。 | 4/5 |
| C｜完整性格包 | 从若干已经写好的气质中直接选择，不能调整。 | 最快、最稳定、最容易控制声音和动作。 | 容易退回“四个人物换皮”，用户创造感和长期个体差异不足。 | 2/5 |
| D｜半打包 | 先选一个起始气质，再调 4–5 个特征的低/中/高。 | 兼顾可理解、可测试与用户所有权；可用起始包处理组合冲突。 | 仍需人格编译、预览和代表性组合评测，不能只靠 Prompt 拼接。 | 3–4/5 |

> 💡 **当前建议，不是确定方案：**优先做 D“半打包”。首版用 4 个可见特征、每个 3 档；等我们证明用户能感知差异、模型能长期稳定后，再考虑增加第 5 个特征或更细的连续滑杆。

## 半打包创建流程建议

1. **选择身份：** 品种、名字、基础外观和声音。
2. **选择起始气质：** 例如“安静观察”“活力好奇”“温柔陪伴”“直接爽快”。这些只是参数起点，不是固定人物，也不带完整背景故事。
3. **调整特征：** 允许把 4–5 个可见特征设为低/中/高；系统实时解释“这会让猫更常主动开口，但不会催促你”。
4. **场景预览：** 用相同的三类场景预览差异，例如“分享好消息”“情绪低落且不想听建议”“向猫征求意见”。
5. **确认并生成性格说明：** 生成一段用户能修改的自然语言说明，同时保留结构化特征作为系统真实依据。
6. **后续调整：** 允许用户在设置中修改，但只影响未来表达；不回写历史记忆，也不假装过去一直如此。

## 性格系统的实现评估

| 工作层 | 关键工作 | 难度 | 主要不确定性 |
|---|---|---|---|
| 特征内容设计 | 给每个档位写清可观察行为、冲突规则、示例与禁区。 | 3/5 | 维度是否互相独立、用户是否理解。 |
| 创建器与预览 | 滑杆/选档、实时解释、固定场景预览和修改反馈。 | 3/5 | 预览能否代表长期体验。 |
| 人格编译 | 把特征编译成有边界的行为策略，再根据状态、关系和场景生成表达；不把原始滑杆直接拼进 Prompt。 | 4/5 | 多特征同时生效时的稳定性。 |
| 组合评测 | 评测代表性角点、特征两两组合和关键场景，而不是穷举所有配置。 | 5/5 | 可辨认性、漂移、边界覆盖与模型版本变化。 |
| 语音与动作映射 | 同一特征同时影响文字、语速、停顿、表情和动作，但不能夸张成刻板表演。 | 4/5 | 跨模态一致性与制作成本。 |
| 长期修改与迁移 | 记录性格版本，保证修改后新行为可解释，历史记忆和关系不被重写。 | 4/5 | 用户是否感到“换了一只猫”。 |

**建议的规则优先级：**安全与用户明确指令 ＞ 用户边界与权限 ＞ 当前场景/状态 ＞ 关系状态 ＞ 稳定人格特征 ＞ 表面语气。这样即使用户把“主动性”和“亲近表达”拉到最高，猫也不能持续催促、占有或拒绝用户离开。

## 人物记忆与关系如何参与表达

记忆不是人格特征。猫应把“它本来是什么性格”和“它后来知道了什么”分开：同样记得用户明天考试，安静型猫可能留下短短一句陪伴，主动型猫可能提前询问准备情况；事实相同，表达策略不同。

关系也不建议压缩成一个亲密度数值。内部可以分别维护熟悉度、信任、已确认边界、共同仪式和共享记忆；外部默认不显示分数，而是通过称呼变化、发起话题的分寸、共同物件、关系日记和动作反馈让用户感知。

## 猫猫世界的三个范围方案

| 方案 | 包含内容 | 取舍 | 难度 |
|---|---|---|---|
| A｜一间猫的家 | 单一房间或小空间，有限状态、动作、玩具和共同物件。 | 最容易让身体与关系落地；内容需求可控，适合作为起点。 | 2–3/5 |
| B｜可扩展猫舍/花园 | 在 A 上增加花园、角落、探索点和逐步解锁的空间。 | 成长感更强，但需要持续美术、状态和内容生产。 | 3–4/5 |
| C｜完整猫猫星球 | 独立文化、地图、NPC、事件与连续世界规则。 | 想象空间最大，但会把产品拉向重内容游戏，并稀释用户—猫关系。 | 5/5 |

**当前建议，不是确定方案：**从 A“一间猫的家”开始，并给未来扩展到 B 留空间。猫可以自己睡觉、玩耍、短暂探索并带回小物；用户可以喂食、玩耍、添置玩具或种花，但这些行为是互动和共同记忆，不是每日强制任务。暂不设计邻居、朋友、主线剧情或“角色故事”话题；猫可以有当下状态和日常行动，但不依赖预写人物小传推动对话。

世界变化应尽量来自可追溯事件库，而不是无限生成的剧情。例如：用户最近完成一场考试，猫把一张“考完了”小纸条放进房间；用户送了新玩具，之后猫的动作池增加。这样既能把聊天和空间连接起来，也更容易保持事实一致。

## 核心对象与边界

> 🧠 **已确认的概念边界：**Agent 本身没有永久记忆。产品所称“长期记忆”，是把经过筛选的信息写入外部存储，并在后续对话中按需检索、注入；当前上下文、长期记忆、话题和日志必须分开建模。

| 对象 | 负责什么 | 如何产生 | 使用边界 |
|---|---|---|---|
| 当前上下文 | 保证本轮及近期对话连贯 | 按窗口、摘要和当前任务自动组装 | 短期有效；不默认永久保存为记忆 |
| 长期记忆 | 保存后续仍可能有价值的稳定信息 | 回复后异步提取候选，经筛选后写入外部存储 | 后续按相关性检索；纠错、删除和禁止使用必须及时生效 |
| 回题候选 | 回答“接下来值得继续什么” | 由当前上下文与召回记忆即时生成并排序 | 可以只存在于当前轮；候选不等于展示，更不等于自动发送 |
| 话题对象 | 保存需要跨时间继续的提问或事项 | 系统把高价值候选持久化，或由用户显式创建 | 具备来源、状态、时间条件、完成和删除生命周期 |
| 反馈与边界 | 约束后续回题与排序 | 来自点赞、点踩、“不要再提”和用户纠错 | 普通点踩用于 Badcase；明确拒绝还需阻断相似话题再次出现 |

## 自动回题如何发生（建议方案）

1. **先回复：** 主对话生成并开始流式返回，不等待记忆抽取或回题生成。
2. **分别提取：** 从新增对话中生成“长期记忆候选”和“后续回题候选”，禁止用一份摘要同时承担两个用途。
3. **分类与筛选：** 判断内容类型、长期价值、置信度、敏感度、是否涉及第三方，以及是否只是短暂情绪。
4. **冲突处理：** 用户明确纠错优先；偏好变化按时间更新并保留变更记录；事实冲突且无法判断时，暂存冲突并在合适时机澄清，不静默覆盖。
5. **写入与关联：** 通过筛选的长期记忆与需要跨时间存在的话题分别写入，并保留来源关联；普通临时候选无需持久化。
6. **检索与决策：** 新对话先从近期表达生成检索问题，召回少量相关记忆，再生成回题候选；系统结合相关性、敏感度、近期展示次数和用户边界，决定继续当前话题、展示候选、稍后发送或保持沉默。

## 长期记忆形成与纠错规则（建议方案）

- **可自动形成：** 稳定偏好、持续目标、明确关系、重要未来事件、反复出现且一致的信息，以及用户明确说“记住”的内容。
- **默认不自动形成：** 一次性闲聊、短暂情绪、模型推断出的心理标签、未核实的第三方隐私，以及高敏感信息。敏感信息是否允许确认后保存，仍需单独定义。
- **错误记忆：** 至少包括事实与用户表达不符、对象或时间归因错误、把推测当事实、旧偏好覆盖新偏好、已删除内容仍被召回。
- **冲突更新：** 显式纠错立即生效；偏好使用“最新有效版本 + 历史变更记录”；无法确认的事实保留竞争状态并降低召回优先级。
- **产品呈现：** 系统必须能追溯来源，但不在自然对话中反复解释。用户在记忆或话题管理处按需查看来源并完成更正、删除和禁止使用。

## 话题库、状态与调度（建议方案）

持久话题建议保存：话题内容、类型、source_memory_id 或来源对话、置信度、敏感度、创建时间、due_at、过期时间、展示次数、状态、完成结果和禁止再次提及标记。字段是否全部进入首版存储由研发评估，但来源、状态、时间条件和用户控制不可缺失。

- **用户定时续聊：** 用户可为话题设置时间；到期后仅在已授权时段以消息触发，并允许延后、完成或取消。
- **系统自动续聊：** 系统可提出候选，但必须结合相关性、敏感度、近期是否已问过和用户边界决定是否展示或发送。
- **入口建议：** 首版优先在聊天顶部或空状态展示少量候选；完整查看、编辑、固定、删除可放入二级管理页。最终位置待交互原型验证。

## 记忆检索与作用域隔离（工程建议）

> 💡 **建议方案，待技术验证：**记忆系统需要同时解决“记住什么、从哪里取、什么时候可以提、用户删除后如何阻断”。语义相关只决定候选，不直接获得发言权限。

| 机制 | 建议设计 | 必须满足的边界 |
|---|---|---|
| 召回组合 | 固定信息、语义相关记忆、最近记忆三路召回；只向主对话注入少量高相关结果。 | 不得把全部历史对话塞入上下文；召回结果需要保留 memory_id、来源和本次使用记录。 |
| 作用域隔离 | 至少按用户、猫、关系实例和主题范围隔离；当前会话、长期记忆、关系日志与话题对象使用不同数据对象。 | 来源或作用域不明确时不自动扩大为全局记忆；服务端必须在检索前后执行作用域过滤。 |
| 冲突与版本 | 显式纠错立即生成新有效版本；旧偏好进入历史版本；无法确认的事实进入 conflicted 状态。 | 不得静默覆盖，不得把模型推断当成用户事实；冲突内容降低召回优先级或暂停使用。 |
| 删除与阻断 | 删除正文、向量索引和相关候选，并保留不含原文的阻断记录；“不要再提”同步关闭相似话题。 | 删除和禁止使用必须早于语义排序生效，防止已删除内容被重新抽取或再次召回。 |
| 检索降级 | Embedding 暂时不可用时，可退化为固定信息与近期记忆；主回复不必因语义检索故障完全不可用。 | 敏感记忆、来源校验和作用域判断不可降级；缺少这些条件时应少说或不提。 |

建议的长期记忆字段至少包括：source_message_id、subject、predicate、value、confidence、sensitivity、scope、status、created_at、last_confirmed_at 和 extractor_version。具体数据库形态与阈值由技术验证决定，不在本 PRD 中提前定案。

## 定时续聊与主动话题触发（工程建议）

定时器只负责重新唤醒系统，不直接生成或发送消息。到期事件仍需进入普通的判断、权限和新鲜度复核链路，最终可以发送、延后、关闭或保持沉默。

| 触发来源 | 处理方式 | 建议阶段 |
|---|---|---|
| 用户明确约定 | 如“明天问我结果”“周五继续聊”；生成 ScheduledFollowUp，保留时区、到期时间、状态和取消能力。 | 数据对象 P0；主动发送 P1 |
| 日期与纪念日 | 到期后创建一次发送尝试；同一事件与时间槽只能派发一次。 | P1 |
| 带时间条件的对话事项 | 先生成 TopicCandidate；通过置信度、敏感度和用户权限门后才可升级为定时续聊。 | P0 候选；P1 外发 |
| 长时间未聊天 | 只生成低优先级候选，不直接发送；需要同时满足主动权限、安静时段、频率和关系阶段。 | P1 后再评估 |

**主动触发流程：**来源事件 → 生成带证据的话题或定时候选 → 指纹去重与冷却 → 到期创建一次发送尝试 → 权限／安静时段／频率／关系阶段／敏感度／近期重复检查 → 重新检查当前会话 → 发送、延后、关闭或沉默 → 记录用户反馈。

# 系统运行、触发与可靠性设计

> 💡 **本部分是建议架构，不是已批准的技术选型。**参考 Cumora 的运行机制和现有 persona16 的工程方法，但猫猫是独立产品，不默认复用其代码、多人结构或本地 Agent 工具。首版目标是让一次回复、一次记忆形成和一次主动触发可恢复、可追溯、可阻断。

## 系统目标与总体链路

1. **用户消息链路：** 消息先持久化 → 安全与边界检查 → 作用域内记忆检索 → 主模型生成 → 发布前新鲜度复核 → 唯一发布组件发送 → 异步生成记忆候选、话题候选、关系日志和运行记录。
2. **主动消息链路：** 到期事件或话题候选 → 权限与频率硬门 → 低成本判断是否值得行动 → 检索相关记忆 → 主模型决定内容或沉默 → 发布前新鲜度复核 → 发送或取消 → 反馈回写。

“可以运行”在本 PRD 中不表示保证模型每次都判断正确，而表示：输入先持久化、重复执行有幂等保护、关键动作经过代码硬门、失败后可以恢复、行为与成本可以回放、必要能力不可用时有明确的降级或停止策略。

## Agent Runtime 与模型适配层（建议方案）

产品逻辑不直接绑定某一家模型。建议通过统一 CatRuntime 接收标准 TurnInput，并输出 TurnResult、工具调用和 usage；Chat、Embedding、后续 ASR／TTS 分别使用适配器。

| 模块 | 职责 | 可靠性要求 |
|---|---|---|
| CatRuntime | 组装当前消息、稳定性格、运行时状态、关系状态、记忆、边界和可用工具；统一输出回复与行动结果。 | 输入输出契约固定；模型供应商变更不改写产品规则。 |
| ChatModelAdapter | 管理主模型、辅助模型、流式输出、超时、重试和供应商降级。 | 同一 Turn 不重复发布；限流或会话损坏时保留可重试状态。 |
| EmbeddingAdapter | 为记忆和话题提供语义表示与检索。 | 故障不阻断普通回复；作用域、安全和删除阻断不可随之失效。 |
| 产品工具层 | 只暴露记忆候选、话题、日程和状态等白名单操作。 | 模型不能直接写底层数据库或绕过权限、幂等和状态机。 |

**模型分工建议：**主模型用于理解、表达和复杂行动选择；辅助模型用于 Triage、分类、候选抽取和压缩；Embedding 用于语义召回。具体供应商和路由策略待成本、延迟与质量评测后决定。

## Wake → Triage → 判断 → 行动或沉默

> 🔔 **核心规则：Wake 不等于发送。**事件只表示“值得看一眼”；系统经过确定性规则和必要的模型判断后，可以立即回复、展示话题、安排稍后处理或保持沉默。

建议的 WakeReason 包括 user_message、voice_turn_end、scheduled_followup_due、topic_due 和 home_state_event。统一输出 ReplyNow、SurfaceTopic、ScheduleLater、StaySilent 四种决策。

- **用户直接消息：** 通过安全检查后必须进入回复路径；不能因为辅助 Triage 故障而永久漏回。
- **主动事件：** 先检查主动权限、安静时段、频率、关系阶段、敏感度和近期重复，再决定是否调用主模型。
- **消息突发：** 短时间连续输入合并为同一处理窗口，避免每条消息各自启动一次完整生成。
- **失败恢复：** 只有成功完成或明确取消才推进事件状态；失败任务保留可重试状态，并通过幂等键避免重复副作用。
- **沉默：** 是合法结果，需要记录沉默原因，但不向用户展示内部技术判断。

## 消息新鲜度复核

模型开始生成时记录 turn_id、input_seq、conversation_version 和 generation_started_at。第一段可见内容发布前，以及最终回复提交前，再与服务端最新会话版本比较。

| 情况 | 处理 | 产品结果 |
|---|---|---|
| 会话未变化 | 通过发布门，提交当前回复。 | 正常流式回复 |
| 用户补充新消息 | 旧草稿标记为 superseded，重新判断继续、修改或取消。 | 避免答非所问或忽略补充 |
| 语音中被打断 | 停止当前 TTS，以新增输入重建回复。 | 形成可打断的自然轮次 |
| 检查服务不可用 | 普通低风险回复可短暂重试；涉及敏感记忆或主动消息时暂停发送。 | 避免过时或越界内容直接外发 |

完全相同的重复回复还应在数据库事务内阻断；语义重复不能只靠字符串比较，需要结合话题指纹、近期回复和结构化对象去重。

## 状态、运行记录与成本账本

产品状态、系统运行状态和关系状态必须分开，不能把技术重试包装成猫猫情绪，也不能把世界场景当成 Turn 是否完成。

| 状态或记录 | 建议内容 | 用途 |
|---|---|---|
| CatWorldState | 睡觉、玩耍、在窗边等世界与场景状态。 | 驱动表现与场景，不判断任务完成。 |
| TurnRunState | queued、triaging、retrieving、generating、completed、failed、superseded。 | 运行恢复、排障和延迟分析。 |
| RelationshipState | 关系阶段、熟悉度、边界和重要变化。 | 约束行为选择，不替代记忆事实。 |
| Run 与 Event | 一次行为的唤醒来源、关键阶段、模型调用、记忆 ID、门控结果和结束原因。 | 回放“为什么回复、为什么主动、为什么沉默”。 |
| 成本账本 | 按 chat、safety、memory_extract、embedding、topic_generate、proactive_gate、voice_asr、voice_tts 分用途记录。 | 成本优化、模型路由和功能毛利评估；估算成本需明确标记。 |

建议关注首字延迟、总延迟、每会话成本、记忆纠错后误召回率、主动消息发送／回复／关闭率、旧回复取消率和异步任务积压。观测写入失败不应阻断普通回复，但必须暴露缺失状态，不能把未知记录伪装成完整数据。

## 后台组件防撞与唯一发布权

首版只有一只用户可见的猫，不需要建立完整多角色发言系统。需要解决的是主回复、记忆抽取、话题生成、关系日志和主动调度并行运行时的重复写入与抢发问题。

- **唯一发布权：** 只有 TurnCoordinator 可以发布用户可见内容；其他组件只能提交候选或发送申请。
- **幂等任务：** 异步任务使用 source_message_id + job_type + version 作为唯一键，重复投递不重复写入。
- **资源认领：** 同一个话题、日程槽或记忆候选只允许一个任务进入最终提交。
- **发布前复核：** 即使任务已获得处理权，也必须通过会话新鲜度、用户边界和重复度检查。
- **未来扩展：** 如果增加多猫或 NPC，再引入私有发言意图与房间仲裁器；不把该复杂度提前带入单猫 P0。

## 阶段、实现难度与首版验收

| 模块 | 难度 | 阶段 | 首个可验收结果 |
|---|---|---|---|
| Runtime 与模型适配 | 4/5 | P0 | 主模型可以替换；模型失败不会造成重复回复；运行用途和 usage 可追踪。 |
| 用户消息 Wake 与 Turn | 3/5 | P0 | 消息先落库；重复事件只执行一次；失败后可恢复且不漏回。 |
| 长期记忆与作用域 | 5/5 | P0 | 来源可追溯；跨会话稳定；纠错、删除和禁止使用后不再召回。 |
| 消息新鲜度复核 | 4/5 | P0 | 用户补充消息后，旧回复可以取消或重建，不会继续发布过时内容。 |
| Run／Event／成本账本 | 3/5 | P0 | 任一回复可回放主要阶段、模型、记忆引用、失败点和成本。 |
| 后台任务防撞 | 3/5 | P0 | 重复队列任务不重复写入；非发布组件无法直接给用户发消息。 |
