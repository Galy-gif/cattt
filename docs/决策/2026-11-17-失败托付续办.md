## 这轮决定

- 只有 `ended/failed` 或 `ended/blocked` 的显式托付可以续办。用户在聊天中明确继续或补充后，`list_tickets` 找到原事项，`update_ticket {text}` 经现有统一入口恢复它；HTTP `PATCH /v1/tickets/:id {text}` 同义。看到失败、时钟扫描或后台重启都不会自动重开。
- 续办保留 ticket、原始授权、旧 run、检查点和模型费用记录；创建递增 generation 的新 run。每次执行仍最多 20 步、8,000 输出 token、10 分钟活动时间，原有供应商暂态重试规则不变。失败预算不被改写，也不在已耗尽的旧 run 上继续累加。
- 每猫仍最多 2 件在办，每个用户本地自然日至多 5 次开工，续办也占一次。日名额记在 run 上，取消、失败及跨日续办不返还已经使用的日名额；超额先排队，扫描只唤醒最新 run。原 `ticket.local_day` 继续表示当前执行准入日。
- 新执行重新读取原托付与全部用户补充，旧模型观察留在历史检查点中，不直接送入新模型请求。原话、补充来源、归属和回避话题在准入时复核，执行和出版继续检查许可与撤回；发生变化时不能使用旧观察绕过检查。
- 失败或受阻事项也可取消，取消后不再进入聊天工具的可续办列表。已完成、已取消、已丢弃的事项不能靠补充恢复。
- HTTP 保留可选 `Idempotency-Key`。成功续办收据含 `resumed: true` 和 `queued`；同键重放返回原收据，不再开一个 run，同键换内容返回 409。普通补充返回值保持原有字段。重放收据只代表当时操作成功，不代表当前状态。
- worker 仍只提交汇报，API 前台复核后回应。续办的聊天回执和 waiting 推送按 run 隔离；推送同时验证当前 run，旧执行即使使用相同工具调用 ID，也不能把旧问题重新推给用户。第一代执行保留历史回执键，旧推送没有 run ID 时只允许对应第一代执行。

本轮入口是聊天工具和 HTTP，未改 iOS“约定与托付”页面；已结束事项仍没有“补一句话”按钮。客户端稳定请求键和最小运行诊断继续留待后续，不将它们标为已完成。普通聊天、时钟和主动推断也没有在本轮全部搬进统一指令入口。
